# 0004. M1에서는 호스트도 익명 세션으로 식별한다

- 날짜: 2026-10-12
- 상태: 채택됨

## 상황

기획서는 호스트를 로그인한 User로 본다 (`Room.hostId` → User). 그런데 소셜 로그인과 Spotify OAuth는 M2에 들어오고, M1의 완료 기준(브라우저 2개에서 큐 동기화)은 방을 만들 수 있어야 검증된다.
M1에서 방을 만드는 사람을 어떻게 식별할지 정해야 방 생성 API의 요청·응답과 테이블 구조가 정해진다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 익명 세션으로 통일 (호스트도 닉네임만) | 계정 없이 YouTube 방을 바로 시연. 게스트 입장과 같은 방식이라 인증 경로가 하나 | `hostId`가 User를 참조하지 않아 기획서 모델과 달라짐. 토큰을 잃으면 호스트 권한을 되찾을 방법이 없음 |
| B. User + JWT를 먼저 | 기획서 모델 그대로 | 소셜 로그인 제공자가 없어 개발용 임시 로그인을 만들어야 하고, M2에서 버리는 코드가 됨 |
| C. 임시 헤더(`X-User-Id`)를 믿기 | 가장 빨리 방·큐 로직에 들어감 | 실무에서 쓸 수 없는 구조. 인증을 붙일 때 컨트롤러와 테스트를 전부 고쳐야 함 |

## 결정

**A를 선택한다.** 방 안의 사람은 로그인 여부와 무관하게 **참여자 ID(UUID)** 로 식별한다.
방 생성(`POST /rooms`)과 게스트 입장(`POST /rooms/{code}/guest`)이 각각 세션을 발급하고, 별도의 세션 발급 API는 만들지 않는다.

세부 결정:

- 세션 토큰은 JWT가 아니라 **불투명 토큰**(SecureRandom 256비트, URL-safe Base64)이다. 세션은 Redis `guest:{token}`에 있고, 강퇴·만료 때 키를 지우면 즉시 무효가 된다. JWT는 만료 전까지 서버가 무효화할 수 없다.
- 세션 하나는 방 하나에 속한다 (`participantId`, `nickname`, `roomCode`). TTL은 방의 수명(6시간)을 따른다.
- 세션에 역할(HOST/GUEST)은 넣지 않는다. 방 안의 권한은 `Room.hostId`와 `RoomMember.role`로 `room` 도메인이 판단한다.

## 결과

- `Room.hostId`, `RoomMember.participantId`는 UUID이고 `user` 테이블을 참조하지 않는다 (`docs/plan.md` §6 수정).
- M2에서 로그인이 들어오면 로그인 사용자도 방에 들어올 때 참여자 ID를 받는다. 그때 `room_member`에 `user_id`(nullable)를 추가해 연결한다. 방·큐·투표 코드는 참여자 ID만 보므로 바뀌지 않는다.
- 아직 토큰을 **검증하는 쪽**(헤더에서 세션을 읽는 코드)은 없다. 토큰이 필요한 첫 API를 만들 때 Spring Security와 함께 넣는다.
- 호스트가 토큰을 잃으면(브라우저 저장소 삭제, 기기 변경) 그 방의 호스트 권한을 되찾을 수 없다. 방은 6시간 뒤 만료된다.
- 재검토 신호: "호스트가 방을 잃어버렸다"는 불편이 실제로 나오면, 로그인 호스트에 한해 계정으로 호스트 권한을 복구하는 경로를 검토한다.
